# CalibForge：通过对抗性求解器校准规模化可学习终端任务

**arXiv**: 2608.06352 | **GitHub**: https://github.com/AweAI-Team/CalibForge | **机构**: 中国人民大学高瓴人工智能学院 + AweAI Team

---

## 一句话总结

CalibForge 提出"对抗性求解器校准"的任务合成范式：让多个 solver 去解候选终端任务，用"强 solver 通过、弱 solver 失败"或"solver 池内部有分歧"作为保留信号，循环修订直到任务落入可学习区间，最终用 5,431 个校准任务把 Qwen3.5-35B-A3B 在 Terminal-Bench 2.0 上训到 47.57%。

## 问题背景

训练终端 agent 需要可执行、可验证、且"难度恰当"的任务——太容易的任务学不到东西，太难的任务模型根本解不出来。现有任务合成系统（TermiGen、SETA、TerminalTraj 等）只验证任务可执行可解，但可执行验证证明不了任务对学习是否有价值。论文的核心观察是：solver 的行为（通过/失败）本身就是任务难度最直接的证据，应该把它变成构造任务的反馈信号。

## 核心方法

- **作者-求解器对抗循环**：作者 agent（DeepSeek-V4-Pro）从线索出发做外部调研、联合编写任务指令/执行环境/验证测试，通过结构校验和自解两阶段验证后，交给 solver 去解；solver 的通过/失败结果和完整轨迹反馈给作者 agent 修订任务，最多 50 轮，直到满足保留准则。
- **多求解器校准（Multi-Solver）**：用三个异构模型（DeepSeek-V4-Flash、GLM-5、Kimi K2.5）独立解同一任务，保留"至少一个成功、至少一个失败"的任务——全过说明太简单，全挂说明太难或有 bug。
- **对比求解器校准（Contrastive）**：指定强 solver（DeepSeek-V4-Pro）必须通过、弱 solver（DeepSeek-V4-Flash）必须失败，把任务钉死在两个 solver 能力区间之间。
- **可学习区间（Learnable Zone）**：两种策略共同定义了一个 solver 相对的可学习区间——任务被证明可解（demonstrated solvability），但又没有被当前 solver 设置"秒杀"。
- **蒸馏训练**：用 DeepSeek-V4-Pro（高推理模式）在最小代码脚手架（只有 bash、文件编辑、finish 三个工具）上蒸馏通过轨迹，全参 SFT 微调 Qwen3-30B-A3B-Instruct 和 Qwen3.5-35B-A3B。

## 关键结果

**Terminal-Bench 2.0（主 benchmark）**，相同蒸馏和训练协议下对比：

| 训练数据 | Qwen3-30B-A3B | Qwen3.5-35B-A3B |
|:---|:---:|:---:|
| Base（无训练） | 7.87% | 39.10% |
| Endless Terminals | 19.48% | - |
| CLI-Gym | 23.22% | - |
| SETA-Env | 23.22% | - |
| TermiGen | 23.60% | 40.07% |
| TerminalTraj | 26.22% | 40.82% |
| **CalibForge** | **32.58%** | **47.57%** |

- 相对最强基线分别提升 **+6.36**（30B）和 **+6.75**（35B）个百分点。
- 跨 benchmark 迁移：30B 相对 base 提升 TB2 +24.71、SWE-bench Pro +27.68（3.26→30.94）、Doc2Repo +30.04（5.94→35.98）；35B 达到 SWE-bench Pro 44.32%、Doc2Repo 48.77%。
- 消融（各 1,300 任务，30B）：无 solver 反馈 22.47% → 单 solver 24.34%（+1.87）→ 多求解器 29.21%（+6.74）→ 对比校准 31.09%（+8.62）。
- 校准过程分析：虽然所有候选都过了结构验证和自解，但进入对比校准时只有 19% 天然满足强-通过/弱-失败关系（61% 是两边都过），经过修订再探测后 96% 被接受；53% 的任务在 5 次探测内搞定，93% 在 20 次内。

## 亮点

- **把"难度"变成可操作信号**：用 solver 行为定义可学习区间，任务难度从拍脑袋变成可验证、可修订的工程指标，这是任务合成从"能解"到"适合学"的关键跃迁。
- **开箱即用**：GitHub（AweAI-Team/CalibForge）和 HuggingFace 数据集（AweAI-Team/CalibForge）都公开了，5,431 个任务 + 蒸馏协议可直接复现。
- **数据多样性实打实**：领域覆盖 16 个类别（最大类软件工程只占 25.5%，对比 SETA-Env 74.6% 集中在系统管理），3,885 个不同能力标签，长尾分布说明不是重复任务的堆砌。
- **消融干净利落**：多求解器和对比校准的增益远超单 solver 反馈，且多求解器轨迹更少却效果更好，排除了"只是数据更多"的解释。

## 局限

- **构建成本高**：每个任务最多 50 轮校准、每次探测 100 步/30 分钟，还要跑多个 solver，全流程成本明显高于"写完就验证"的现有方案。
- **solver 相对性**：可学习区间是相对于特定 solver 池定义的（强=DeepSeek-V4-Pro、弱=DeepSeek-V4-Flash），换个 solver 池任务集的"难度分布"可能漂移，校准准则的普适性待验证。
- **蒸馏依赖单一老师**：轨迹全部由 DeepSeek-V4-Pro 蒸馏，训练目标（Qwen 系列）也有限，老师-学生组合的泛化性没有展开测试。

## 个人评价

这篇对我的启发很大。终端任务合成一直有个隐性矛盾：验证器只能证明"任务可解"，但训练需要的是"任务在模型能力边缘"——而 CalibForge 用最朴素的方式解决了它：既然不知道难度在哪，就让 solver 去试，用 solver 之间的分歧来刻画难度。这其实是把"课程学习"的思想下放到了数据构造阶段：不需要显式难度曲线，一个强-弱 solver 对就天然定义了从易到难的区间。

另一个值得借鉴的点是"修订而非过滤"：81% 的候选第一轮不满足目标关系，但经过反馈驱动的修订后 96% 被接受。也就是说大多数"不合格"任务不是废料，而是缺一次针对性的调整——这跟 agent 训练里的迭代调试思路一脉相承。对做 GWS 数据管线的启发：任何"生成→验证"的流程，都可以加一层"对抗者"来校准数据难度，而不是只做二元过滤。
