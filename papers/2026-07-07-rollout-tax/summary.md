# The Rollout Infrastructure Tax in Coding-Agent Reinforcement Learning

**arXiv**: 2607.01415 | **GitHub**: 无 | **机构**: Daytona (industry)

---

## 一句话总结

本文系统性测量了 coding-agent RL 中的执行基础设施开销，发现不同执行底层间冷启动延迟相差高达 110x，在百万级轨迹规模下工作小时散布达 1.8x。

## 问题背景

Coding-agent RL 的每个 rollout 不仅依赖于模型推理和奖励计算，还依赖于执行环境的提供和管理。这部分“基础设施税”在当前研究中被忽视，但小延迟在大规模训练中会大幅累计。最近的代理RL系统报道 rollout 生成可占总运行时间的 90% 以上，显示这不仅是“部署管道”而已。

## 核心方法

1. **定义 Rollout Infrastructure Tax**: 系统性识别组成运行开销的操作: 环境创建、准备、编排、命令执行、观察收集、清理
2. **对比测试 4 种执行底层**: 单独 container、hosted sandbox、Kubernetes 编排 container、云 VM
3. **控制变量实验**: 在相同的 coding-agent 工作负荷下对比 substrate 延迟
4. **投影计算**: 将测量结果投影到百万级轨迹规模，计算对工作小时的影响

## 关键结果

| 指标 | 结果 |
|---------|--------|
| 冷启动延迟变化 | 最大 110x |
| 1M 150-step 轨迹工作小时散布 | 1.8x (5,316 额外工时) |
| 1s/rollout 额外延迟 | 1M 轨迹→ 278 额外工时 |
| 10ms/action 额外延迟 | 1M×150 steps → 417 额外工时 |
| 100ms/action 额外延迟 | 1M×150 steps → 4,167 额外工时 |
| Rollout 占总运行时间 | 可达 >90% |

## 亮点

1. **独特视角**: 大部分 agentic RL 论文关注算法，这篇从系统工程角度揭示了被忽视的基础设施开销
2. **数据驱动**: 110x 冷启动差异是一个惊人的数字，直接指向工程优化空间
3. **可执行建议**: 提出三个具体设计要求: locality-aware warm pools、low-latency action APIs、isolation 按 rollout 大小分级
4. **实用性强**: 对任何构建大规模 agentic RL 系统的团队都有直接参考价值

## 局限

1. **无开源代码**: 仅是测量报告，没有发布可复现的 benchmark 或工具
2. **简短**: 6 页短文（ACM SoCC 2026），深度有限
3. **单一场景**: 仅聚焦 coding-agent，未涵盖其他类型的代理系统

## 个人评价

这篇文章的价值在于“让你意识到了一个你知道它存在但从未真正量化过的问题”。对我们的启示是: (1) 当你在大规模训练 agent 时，首先询问“我的执行底层有多慢”，而不是直接去优化算法; (2) 冷启动延迟 110x 的差异意味着选择合适的执行底层比优化算法更能提升整体效率; (3) 未来的 agent RL 框架应该把执行底层作为第一类 citizens 设计，而不是事后插件。
